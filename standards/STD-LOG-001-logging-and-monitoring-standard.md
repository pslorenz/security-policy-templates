## 1. Purpose

This standard defines how [ORGANIZATION_NAME] collects, retains, protects, and monitors security logs. It sets the specific requirements that other policies in the suite depend on: the centralized endpoint logging in POL-EP-001 Section 3.7, the evidence preservation in POL-IR-001 Section 3.8, and the program metrics in POL-GOV-001 Section 3.11.

Logs serve two purposes, and both matter. The first is detection: noticing that something is wrong while there is still time to limit the damage. The second is investigation: reconstructing what happened after the fact, which determines what was accessed, whether notification obligations apply, and whether the adversary is gone. A program that collects logs nobody watches fails the first purpose. A program that watches alerts but keeps logs for only a week fails the second.

The most common logging failure in small and mid-sized organizations is discovering, in the middle of an incident, that the logs covering the critical period expired before anyone looked for them. Cloud platforms retain their native logs for shorter periods than most people assume. This standard exists to close that gap before it matters.

As a standard under POL-GOV-001 Section 3.4, this document is approved by the Information Security function. The initial version is also approved by the executive sponsor because retention periods carry ongoing storage costs.

## 2. Scope

This standard applies to security-relevant logs generated by any system in scope of POL-AM-001, including:

Identity providers and directory services. Email and collaboration platforms. Endpoints and servers. Network and perimeter devices, including firewalls, VPN gateways, and DNS services. Cloud platforms and their control planes. SaaS applications that hold Confidential or Restricted data under POL-DC-001. Backup and recovery systems. Security tools, including EDR, email security, and vulnerability management platforms.

It applies to logs generated by service providers on [ORGANIZATION_NAME]'s behalf, as described in Section 3.11.

Application performance logs, debug logs, and other operational logs without security relevance are out of scope unless they are needed for a specific investigation.

## 3. Standard Requirements

### 3.1 Log Sources

Log sources are divided into two tiers. Required sources are collected by every organization adopting this standard. Recommended sources are collected where the system exists and the central logging platform supports it.

**Required sources:**

Identity provider sign-in logs, including successful and failed authentication, MFA outcomes, and Conditional Access results, for both users and non-human identities governed by POL-IAM-003 (for example, Microsoft Entra ID interactive, non-interactive, service principal, and managed identity sign-in logs). Identity provider audit logs, including user, group, role, application, and policy changes (for example, Microsoft Entra ID audit logs). Email and collaboration platform audit logs, including mailbox access, mail forwarding rules, file sharing, and administrative actions (for example, the Microsoft 365 unified audit log). Endpoint detection and response telemetry and alerts from every endpoint covered by POL-EP-001. Firewall and VPN logs, including allowed and denied connections at the perimeter and remote access sessions. Windows security event logs from servers and domain controllers, where present. Backup system logs, including job results, retention changes, and deletion of backup data.

**Recommended sources:**

DNS query logs. Web proxy or secure web gateway logs. Cloud control-plane logs (for example, Azure Activity logs, AWS CloudTrail, GCP Cloud Audit Logs). Administrative audit logs from SaaS applications holding Confidential or Restricted data. Email security gateway logs. Command-line and PowerShell audit logging on servers. Vulnerability management platform findings. Microsoft Graph activity logs, which record API requests made by applications and users against the tenant and exist only where they are exported.

Backup logs are a required source because attackers target backups before deploying ransomware. Deletion of backup data or changes to backup retention are high-priority signals.

The current list of log sources and their collection status is maintained in TPL-LOG-001, and is reviewed when systems are added or retired under POL-AM-001.

### 3.2 Central Logging Platform

Required log sources are forwarded to a central logging platform where they can be searched together, correlated, and monitored. Native consoles in individual products are not a substitute; an investigation that requires logging in to eight separate consoles is an investigation that will miss things.

The approved central logging platform for [ORGANIZATION_NAME] is [CENTRAL_LOGGING_PLATFORM, e.g., a cloud-native SIEM, a managed SIEM service, or the SIEM operated by the designated security service provider].

### 3.3 Collection and Timeliness

Logs reach the central logging platform within fifteen minutes of the event, consistent with POL-EP-001 Section 3.7. Sources that cannot meet this timeline are documented with their actual latency.

The central logging platform alerts when a required source stops sending logs. A source that has been silent for more than twenty-four hours is investigated. Attackers disable logging to cover their activity, and a silent source is treated as a potential security event until it is explained.

### 3.4 Time Synchronization

All systems that generate logs synchronize their clocks to authoritative time sources, using at least two sources where the system supports it. On-premises systems synchronize to [TIME_SOURCE, e.g., the domain hierarchy, with the PDC emulator synchronized to two or more public NTP sources]. Cloud services use their platform's time source.

The central logging platform normalizes timestamps to a single time zone, [LOG_TIME_ZONE, e.g., UTC]. Incident timelines under POL-IR-001 use the same time zone.

### 3.5 Retention

Security logs from required sources are retained for:

**Searchable retention: at least ninety days.** Logs are immediately searchable in the central logging platform for ninety days. This covers typical attacker dwell time and the investigation that follows.

**Total retention: at least one year.** Logs older than ninety days may move to lower-cost archive storage, provided they can be restored for investigation within [ARCHIVE_RESTORE_TIME, e.g., two business days].

**Extended retention.** Logs related to an incident under legal or regulatory process are preserved for the period determined with legal counsel under POL-IR-001 Section 3.8, regardless of the standard retention period. Where a legal, regulatory, or contractual obligation listed under POL-GOV-001 Section 3.10 requires longer retention, the longer period applies to the affected logs.

Recommended sources are retained for at least ninety days.

### 3.6 Microsoft Cloud Logs

Microsoft cloud services retain their native logs for limited periods. As of this version, Microsoft Entra ID retains sign-in and audit logs for seven days on the free tier and thirty days on P1 or P2, and the Microsoft 365 unified audit log retains standard audit records for 180 days. Logs that age out of Microsoft's retention cannot be recovered. Verify current retention periods against Microsoft's documentation at each annual review, as they change.

For organizations using Microsoft 365 and Microsoft Entra ID:

**Entra ID logs are exported.** Entra ID sign-in logs and audit logs are exported through diagnostic settings to the central logging platform. Relying on Entra ID's native retention does not meet Section 3.5. Diagnostic settings export requires Entra ID P1 or P2, which is included in Microsoft 365 Business Premium, E3, and E5. Tenants without P1 or P2 document the gap as an exception under Section 3.12 with a plan to address it.

**Unified audit logging is verified as enabled.** The Information Security function confirms that unified audit logging is turned on for the tenant and that mailbox auditing is active, and rechecks both at each annual review.

**The unified audit log is collected.** Unified audit log records are collected into the central logging platform through its Microsoft 365 integration, so that they are retained for the full period in Section 3.5 and can be correlated with other sources.

**Defender alerts and telemetry are collected** where Microsoft Defender products are in use, through the central logging platform's integration.

### 3.7 Optional Immutable Archive for Microsoft Logs

Organizations may add a second, independent storage layer for Microsoft cloud logs: an Azure Storage general-purpose v2 account with an immutable (write once, read many) retention policy. This layer is optional. It is recommended for organizations with elevated risk, regulatory evidence requirements, cyber insurance conditions that call for tamper-evident logs, or a central logging platform operated by a third party whose retention [ORGANIZATION_NAME] does not control.

The immutable archive protects against a specific scenario: an attacker, or a compromised administrator account, deleting or altering logs to conceal activity. A locked immutability policy prevents deletion or modification by anyone, including global administrators and subscription owners, until the retention period expires.

Where the immutable archive is implemented, it meets the following requirements:

**Dedicated storage account.** The archive uses a general-purpose v2 storage account used only for log archiving, with no other data stored in it. Where the logged resource is regional, the storage account is in the same region.

**Sources.** Entra ID sign-in and audit logs and Azure Activity logs are sent to the archive through diagnostic settings, as a second destination alongside the central logging platform. Other Microsoft logs, such as the unified audit log and Defender data, are sent to the archive where a supported export path exists, such as a streaming or data export feature, and the path's compatibility with immutable storage has been confirmed.

**Immutability policy.** The log containers have a time-based retention policy set to at least the total retention period in Section 3.5 (365 days by default). Because diagnostic settings write to append blobs, the policy has protected append writes enabled; without it, log delivery fails. Where an account-level default policy is used instead of container-level policies, the account has version-level immutability support enabled, which requires blob versioning, and append delivery is confirmed during validation.

**Lock after validation.** The policy is created unlocked, log delivery is verified for every source over at least [VALIDATION_PERIOD, e.g., seven days], and the policy is then locked. A locked policy cannot be shortened or removed, only extended, and the setting for protected append writes can no longer be changed. Locking is a deliberate, irreversible decision approved by the Information Security function.

**Access control.** The storage account is placed in a separate resource group or subscription from production workloads. No user or application identity holds a data-plane write or delete role on the account; log delivery is the only writer. Owner and Contributor assignments on the account are limited to named administrators, because those roles can retrieve account keys while shared key access is enabled. Read access is limited to named members of the Information Security function and the incident response team. Shared key access is disabled where the log delivery path supports it, and an Azure resource lock prevents deletion of the storage account.

**Network access.** If the storage account's firewall is enabled, trusted Microsoft services are allowed through so that diagnostic settings can deliver logs.

**Expiry and cleanup.** Diagnostic settings no longer apply retention to logs sent to storage. A lifecycle management rule deletes blobs after the retention period expires, so the archive does not grow indefinitely.

**Legal hold.** When an incident under POL-IR-001 requires preservation beyond the standard period, a legal hold is applied to the affected containers. The hold is removed only when legal counsel confirms preservation is no longer required.

**Cost awareness.** Data in a locked container cannot be deleted early, and the storage account cannot be deleted while it holds protected data. The executive sponsor approves the expected storage cost before the policy is locked.

The configuration of the immutable archive, including the storage account, containers, retention period, and lock date, is recorded in TPL-LOG-002 and verified at each annual review.

### 3.8 Log Protection and Access

Logs are evidence, and they are protected accordingly.

Access to the central logging platform and log archives is restricted to the Information Security function, the IT function where operationally required, and the designated security service provider. Access follows POL-IAM-001, including phishing-resistant MFA for administrative access.

Administrators of a system cannot delete or modify the logs of their own actions on that system. Where the central logging platform permits deletion, deletion rights are restricted to a role separate from day-to-day administration.

Changes to logging configuration, including disabling a log source, reducing retention, modifying diagnostic settings, or turning off audit logging, generate alerts in the central logging platform.

Logs that contain personal data or Confidential data are handled under POL-DC-001.

### 3.9 Monitoring and Alerting

The central logging platform is monitored for security events. Monitoring is performed by [MONITORING_PROVIDER, e.g., the Information Security function, or the designated MDR/SOC provider] with [MONITORING_COVERAGE, e.g., 24x7 coverage, or business-hours coverage with automated containment outside business hours].

Alerts are triaged within the following timelines, aligned with the severity levels in POL-IR-001 Section 3.2:

**Critical alerts** (for example, ransomware behavior, confirmed credential theft with active sign-ins, mass deletion of backup data): triaged within thirty minutes, at any hour where 24x7 monitoring is in place. Where monitoring is business-hours only, Critical alerts trigger automated containment through the authority matrix in POL-IR-001 Section 3.5 and notification to an on-call contact.

**High alerts**: triaged within two hours during monitoring hours.

**Medium alerts**: triaged within one business day.

**Low alerts**: reviewed weekly.

At minimum, the central logging platform alerts on:

Risky or anomalous sign-ins, including impossible travel and sign-ins from anonymizing infrastructure. New inbox rules that forward, redirect, or delete mail, and new external mail forwarding. Changes to MFA methods on user accounts. Changes to Conditional Access policies. Assignment of administrative roles. New OAuth application consent grants with broad permissions. New credentials, secrets, or certificates added to application registrations or service principals. Changes to domain federation settings or the addition of federated domains. Device code authentication, where it is not an approved sign-in method. EDR detections at the platform's high or critical severity. Mass file deletion, encryption, or download. Deletion of backup data or changes to backup retention. Disabling of logging or security tools. Legacy authentication attempts, where legacy authentication is blocked.

Detection rules are reviewed at least annually and after each post-incident review, so that lessons from incidents become detections.

### 3.10 Log Review

Beyond alert triage, the Information Security function or the monitoring provider reviews the prior week's alert activity and closed alerts at least weekly, looking for related events that were triaged individually but belong together.

The Information Security function reviews log data at least monthly for longer-running patterns that do not trigger individual alerts, such as gradual increases in failed authentications, accounts signing in from new locations, or dormant accounts becoming active.

Log source health is reviewed monthly: which sources are reporting, which have gaps, and whether collection meets the timeline in Section 3.3.

Monthly review findings feed the metrics reported under POL-GOV-001 Section 3.11, including log source coverage and alert volumes by severity.

### 3.11 Service Provider Logs

Where a service provider operates systems or monitoring on [ORGANIZATION_NAME]'s behalf, the service agreement addresses: which logs the provider collects and retains, the retention periods, how [ORGANIZATION_NAME] can obtain logs for an investigation, and what happens to the logs when the relationship ends.

Logs held by a service provider count toward the retention requirements in Section 3.5 only if [ORGANIZATION_NAME] can obtain them within the restore time in that section. Where that is not assured, the immutable archive in Section 3.7 or another [ORGANIZATION_NAME]-controlled copy is used.

### 3.12 Exceptions

Exceptions to this standard follow the process in POL-GOV-001 Section 3.6. Common exceptions include systems that cannot forward logs in a supported format, licensing that does not support log export, and storage cost constraints on retention. Each exception documents the gap, the compensating controls, and the plan to close it.

## 4. Roles and Responsibilities

**Information Security function.** Owns this standard. Maintains the log source inventory and detection rules. Monitors or oversees monitoring of the central logging platform. Performs monthly log reviews. Approves locking of the immutable archive policy. Verifies Microsoft logging configuration at each annual review.

**IT function (or IT service provider).** Configures log forwarding, diagnostic settings, and time synchronization. Configures the immutable archive where implemented. Restores logs from archive for investigations. Notifies the Information Security function before changes that affect log sources.

**Monitoring provider (where designated).** Triages alerts within the timelines in Section 3.9. Escalates incidents under POL-IR-001. Reports monitoring metrics.

**Executive sponsor.** Approves the initial version of this standard and the storage costs of retention and the immutable archive.

**Legal counsel.** Determines extended retention and legal hold requirements for logs related to incidents and legal matters.

## 5. Enforcement

Gaps in logging are addressed as security findings rather than disciplinary matters in most cases. Specific remediation timelines:

A required log source not reporting to the central logging platform: investigated within one business day and restored within seven days, or documented as an exception.

Microsoft Entra ID logs not exported where P1 or P2 licensing exists: remediated within fourteen days of identification.

Logging disabled or retention reduced without approval: treated as a potential security incident under POL-IR-001 until explained.

Deliberate deletion or alteration of logs to conceal activity is treated as concealment of evidence under POL-IR-001 Section 5 and may result in serious disciplinary action up to and including termination.
